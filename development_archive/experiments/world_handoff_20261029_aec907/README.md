## 3. 当前求解的问题定义

仅讨论普通固定牌型、无道具、无移出区、无复活、无变色的情况：

- 每张牌有唯一 ID、牌型 type、层号 layer、坐标 rolNum / rowNum。
- 高层牌 b 覆盖低层牌 a，当且仅当 `b.layer > a.layer` 且横、纵坐标差的绝对值都小于 8。
- 只有全部覆盖者已取走的牌可以点击；每步取一张。
- 同类型累积到三张立即消除；模型要求每步三消结算后槽内不超过 6 张。
- 胜利要求所有牌取完且牌槽为空。实际游戏规则与覆盖关系的准确性仍是模型成立的前提。

在本局空槽起点下，状态可以写成已取集合 D：

`tray[type] = 已取的该类型张数 mod 3`

因此相同 D 的不同取牌顺序会到达相同的普通牌局面。搜索必须允许分支回退，但不必重复搜索所有相同集合的排列。这一简化不能直接套到变色、道具缓冲区或其他动态规则上。

当前原始数据、规范化牌表和全部覆盖关系已放入交接资料。提出新算法时可以直接使用 `current_problem.json`，不必先处理抓包或截图。

## 4. 应用现在实际怎样计算

主要入口是 `static_plan.py`，不是只调用最初的 Python normal。

| 阶段 | 当前行为 |
|---|---|
| 完整答案缓存 | 核对原始地图 SHA、规则和已确认前缀，完整回放通过后才复用 |
| 小图 | 剩余不超过 60 张时直接走整局 CP-SAT；第一关属于此类 |
| 大图快速阶段 | 最多约 12 秒，同时启动 1 路 tight-top 和 3 路不同策略的束搜索 |
| 候选诊断 | 最多保留 3 条合法部分路线，独立核查残局并向前回退，提取已证死状态约束 |
| 整局约束阶段 | 用剩余预算运行 CP-SAT，部分路线仅作软提示，已证死状态作约束 |
| 执行 | 只有完整路线通过独立回放并完成实机对齐后才点击；部分候选不能执行 |

本局快速阶段的实际结果：

| 策略 | 用时 | 最深步数 | 退出原因 |
|---|---:|---:|---|
| tight-top | 3.51 秒 | 193 | **state_limit，2000001 个状态** |
| static-beam-safe | 2.97 秒 | 144 | beam_frontier_empty |
| static-beam-balance | 5.63 秒 | 138 | beam_frontier_empty |
| static-beam-dig | 5.71 秒 | 141 | beam_frontier_empty |

束搜索截断保留了部分状态，因此其 frontier_empty 不能用来证明全图无解。


最初的 1.5 秒额外时间截断已删除，**200 万状态上限仍在**。原生程序是 DFS 加排序和短步消除可达性剪枝，与原版 Python normal 并非完全相同策略，不能把差距全部归因于编译语言。

## 5. “还剩几十张”为什么不能直接固定前面

本局三条部分候选的独立检查，分别证明以下已取集合无法继续清空：

| 对应候选 | 已证死前缀长度 | 剩余牌数 | 独立检查状态数 |
|---|---:|---:|---:|
| 最长 193 步候选 | 145 | 86 | 26713 |
| 144 步候选 | 120 | 111 | 4060 |
| 141 步候选 | 117 | 114 | 3070 |

这证明的是这些前缀对应的局面无后续解，**不是整张图无解**。

对最长候选来说，固定前 145 步选出的牌集合以后，后续无论怎样搜索都走不完。从第 193 步只回退最后 10 步，仍保留了那个死状态。要避开它，必须更早改变前 145 步选出的牌集合；只重排同一集合也不能改变牌槽余数和剩余覆盖关系。

这是“深度高不等于接近通关”的本局具体证据。边算边执行未经完整验证的长前缀，会把可撤回的搜索错误变成实机无法撤回的局面。

前两条答案经过原始地图 SHA 绑定、独立规则回放、Python 回放和 C# `--validate-only` 检查。本次整理又重新核对了原始地图和答案，两条仍合法；尚未实机执行这两张图的完整第二关。

基准 tight-top 的参数为 `solve_first=0.8`、4000 万状态上限；与应用默认的 `0`、200 万不同。它们至少应先做同图、同预算的参数对照，不能把基准胜出的配置等同于应用已经采用了它。

基准后曾对一张已知可解旧世界图做过顺序复查：仅把原 1.5 秒上限改成 10 秒，其他保持 `solve_first=0`、200 万状态，就在约 2.62 秒出解；另一组 `0.8`、200 万触及上限，改到 4000 万后约 4.92 秒出解。这些结果属于旧图，不是当前 d91a 图的保证。

实验边界：

- 植入图带有生成偏差，20 张样本不能代表所有实际游戏地图。
- 随机图仅 3 张已知可解，其余 17 张都是未知；不能据此称“85% 无解”。
- 随机重排分布不等于游戏服务器出题分布。
- CP-SAT 在本轮预算内表现较弱，不代表所有约束模型都差。事后给它固定的、经支配规则定序的已知见证时，25 张已知正例都被接受；这项核查不计入出解率，也不等于整个模型已被全面证明正确。

## 7. 哪些已经查明，哪些还不确定

**已经查明：**

- 两张旧世界关确实有完整无道具解，“世界关普遍不可解”的早期推断不能成立。
- 当前新图没有特殊牌，不需要靠特殊卡牌规则来解释这次失败。
- 当前应用不是单一算法用满 300 秒；原生策略被状态上限提前停止后，剩余预算主要投入 CP-SAT。
- 已有部分提示时，当前加速器会跳过新的原生候选生成；再次点击开始并不自动意味着换种子或真正续上原生搜索树。
- 完整答案有精确缓存；部分路线和 3 条死状态约束也会保存。**CP-SAT 的全部内部学习及原生 DFS 的整棵搜索状态没有作为当前默认流程的完整断点保存。**
- 项目已有 `DeadStateCache.cs`，但本局默认传入的 prefix 文件仅包含 sequence 和 map_sha256，没有接入该跨进程死状态缓存接口。不能把“有这个代码文件”当成“本局已在使用”。

**仍不确定：**

- 当前 d91a 图在此无道具普通牌模型下是否可解。
- 按基准胜出的原生参数给足状态预算后，当前图能否快速出解；本次整理没有启动这一实验。
- 覆盖关系、槽时序与当前客户端全部边缘情况是否完全一致。离线合法不等于已完成实机通关。
- 当前图的困难主要来自搜索排序、实现/模型问题，还是实例自身难度；现有两张正例不足以区分全部原因。
- 是否值得加入道具模型。当前尚没有无道具无解证据，因此还不能把道具作为必要条件。

## 8. 建议别人优先给意见的具体问题

1. **先如何建立正确默认基线？** 当前图做 `solve_first∈{0,0.8}`、状态上限 `∈{200万,4000万}` 的对照，记录完整解、退出原因、状态数、CPU/墙钟时间。是否应优先走原生 DFS，而不是立即转入目前较弱的 CP-SAT？
2. **如何利用已证死的已取集合？** 当前 3 条约束排除了若干错误中段，但信息很稀疏。怎样安全地共享、持久化完全穷尽的状态，并减少相同 D 的重复计算？超时中断的局面不能冒充已证死局。
3. **怎样修正早期排序？** 本局已有 145 步死状态证据。哪些结构性启发式或有限偏差/重启策略，能在已知正例基准上验证有效，而不是继续只看最长前缀？
4. **若要判断无解，使用什么可复核手段？** 当前没有 SAT/DRAT 等独立证书。CP-SAT UNKNOWN 不作判定，束搜索失败也不作判定。精确层宽探测可以先做，但应实测状态数和实际内存；231 位的 32 字节仅是净位集，不含哈希、父指针、扩容和工作集。
5. **何时扩展到道具？** 应先明确可用次数、移出区再取规则、撤回和复活状态，再讨论“最少道具通关”，而不是把它们隐含在普通牌模型里。

本阶段更合适的目标是：**在有真值的正例上验证算法，再把同一设置用于当前未知图；每一步都区分“完整解 / 未知 / 经确认的无解”。**
